Routes define how incoming requests are matched and forwarded to your upstream services. Every request that reaches your gateway is evaluated against your configured routes, and the first match determines where that request goes and which policies apply to it.

## Route Anatomy

A route is built from five core fields. Configure each one to precisely control which traffic a route captures and how it forwards that traffic.

<CardGroup cols={2}>
  <Card title="path" icon="route">
    The URL pattern to match against the incoming request path. Supports exact matches like `/api/v1` and prefix matches using the `/*` wildcard, such as `/api/v1/*`.
  </Card>
  <Card title="methods" icon="arrow-right-arrow-left">
    The HTTP methods this route accepts. Choose any combination of `GET`, `POST`, `PUT`, `DELETE`, and `PATCH`. Requests using an unlisted method are not matched by this route.
  </Card>
  <Card title="upstream" icon="server">
    The full backend URL that matching requests are forwarded to — for example, `https://api.example.com/service`. Mysoleas proxies the request to this address after route matching and policy evaluation.
  </Card>
  <Card title="strip_path" icon="scissors">
    When set to `true`, Mysoleas removes the matched path prefix before forwarding the request. For example, a request to `/api/v1/users` matched by `/api/v1/*` would arrive at your upstream as `/users`.
  </Card>
  <Card title="preserve_host" icon="globe">
    When set to `true`, Mysoleas passes the original `Host` header from the client request to your upstream instead of replacing it with the upstream hostname. Useful when your upstream uses virtual hosting.
  </Card>
</CardGroup>

## Path Matching Rules

Mysoleas supports two path matching strategies:

- **Exact match** — The route only matches requests whose path is identical to the configured `path` value. A route with `path: /api/v1` matches `/api/v1` only.
- **Prefix match** — Append `/*` to capture the configured path and anything beneath it. A route with `path: /api/v1/*` matches `/api/v1`, `/api/v1/users`, `/api/v1/orders/123`, and so on.

### Match Examples

| Path Pattern   | Example Request        | Matched? |
| -------------- | ---------------------- | -------- |
| `/api/v1`      | `/api/v1`              | ✅ Yes   |
| `/api/v1`      | `/api/v1/users`        | ❌ No    |
| `/api/v1/*`    | `/api/v1`              | ✅ Yes   |
| `/api/v1/*`    | `/api/v1/users`        | ✅ Yes   |
| `/api/v1/*`    | `/api/v2/users`        | ❌ No    |
| `/health`      | `/health`              | ✅ Yes   |
| `/health`      | `/healthz`             | ❌ No    |

## Route Priority and Evaluation Order

When a request arrives at your gateway, Mysoleas evaluates all active routes in **priority order** and forwards the request using the **first matching route**. Lower priority numbers are evaluated first.

<Warning>
  If two routes can match the same request, only the higher-priority route (lower priority number) will handle it. Review your route priorities whenever you add a new route to avoid unintended shadowing.
</Warning>

As a general rule, define more specific routes with higher priority than broad wildcard routes. For example, give `/api/v1/admin/*` a higher priority than `/api/v1/*` so admin traffic is handled by its dedicated route.

## Route Status

Each route can be set to **active** or **inactive** independently of the gateway's own status. Deactivating a route causes Mysoleas to skip it during evaluation — the gateway returns `404` for requests that would have matched only that route.

<Tip>
  Use inactive routes to stage new routing configurations before making them live, or to temporarily disable a specific upstream without removing the route entirely.
</Tip>
